# План тестування — КП №3

## 1. Мета та область

Перевірити готовність web-застосунку спортзалу «Ритм» після КП №1–2: клієнтські сторінки, реєстрацію та JWT-автентифікацію, каталог тренувань, записи користувача, адміністративний CRUD, REST API, валідацію і взаємодію з PostgreSQL.

## 2. Об'єкти тестування

- сторінки `index.html`, `trainings.html`, `strength-training.html`, `about-gym.html`, `training-signup.html`, `account.html`, `admin.html`;
- форми реєстрації, входу, запису та редагування;
- `/api/auth/*`, `/api/categories`, `/api/trainings/*`, `/api/bookings/*`, `/api/health`;
- ролі `member` і `admin`, ізоляція записів користувачів;
- серверна валідація ID, email, пароля, дат, телефону, тренувань;
- цілісність даних PostgreSQL та HTTP-коди 200/201/204/400/401/403/404/409.

Поза областю: навантажувальне тестування production-інфраструктури, платіжні системи та зовнішні інтеграції, яких у проєкті немає.

## 3. Стратегія та види тестування

1. Ручне функціональне тестування методом чорної скриньки: позитивні, негативні та межові сценарії у Chromium.
2. Unit-тестування методом білої скриньки: чисті схеми й функції модуля `server/validation.js` через вбудований `node:test`.
3. Інтеграційне API-тестування: `Supertest` викликає реальний Express та локальний PostgreSQL; тестові дані видаляються після прогону.
4. Перевірка безпеки: відсутність підвищення ролі при реєстрації, 401 без JWT, 403 для member на admin-маршруті, хешування паролів.
5. Регресійне тестування після виправлень: повторний `npm test` і ручна перевірка пов'язаних сценаріїв.

## 4. Середовище

- Node.js 26.13.0, npm 12.2.2;
- Express 5, PostgreSQL 17.11 у Docker Compose;
- Chromium, desktop 1440×900;
- Linux, локальна адреса `http://localhost:3000`;
- тестові фреймворки: `node:test`, Supertest 7.1.4, вбудований V8 coverage.

## 5. Вхідні та вихідні критерії

Вхідні критерії: БД має статус healthy, схема ініціалізована, серверні залежності встановлені, `.env` створений, застосунок запускається.

Критерії завершення:

- виконано щонайменше 5 ручних, 5 unit і 5 API-тестів;
- 100% тестів поточного набору мають статус Passed;
- немає відкритих Critical або Major дефектів;
- усі знайдені дефекти мають баг-репорти та картки на GitHub Projects;
- сформовано coverage і підсумковий звіт;
- після виправлень виконано повну регресію.

Критерій призупинення: БД/сервер не запускається або дефект блокує більшість сценаріїв. Відновлення — після усунення причини та smoke-перевірки `/api/health`.

## 6. Ризики

- локальне оточення може відрізнятися від production;
- автоматизовані API-тести потребують доступної PostgreSQL;
- coverage показує виконані рядки, але не доводить відсутність усіх дефектів;
- часові межі дат залежать від системного UTC-часу сервера.

## 7. Команда запуску

```bash
docker compose up -d --wait db
npm run db:init
npm test
```
